## Why A-4's original definition is stale

DESIGN's A-2 note says A-4 should "split `Entry` into a client data block and a
TUI fold view, and let the client organise `landed`'s `Record::Seal`". That was
written before A-3. On the only remaining entry point:

- `Tui::for_pipe` -> `Panes::new()` -> `Log::without_cache()` ->
  `WindowJournal::new()` -> `Cache::none()`. `Log::write` / `record_seal` /
  `landed`'s `rewrite` therefore have nowhere to write.
- `CursorMessage` is consumed inside the client and never crosses the pipe;
  `apply_frame` handles the 12 drawing `RenderMessage` variants and 6 control
  frames only. Nothing calls `Log::landed` / `rewind` / `older` / `stamp`.
- The client's own `WindowJournal` holds a real `Cache`, but `consume(Landed)`
  appends `Floor` + `Stamp`; history rows are replayed by the server, not read
  from local `Seal` records.

So moving `Entry`'s data blocks into the client would give a second process a
copy of the window's rows that nobody reads. Two directions are now in
`DESIGN.md` §1, "A-4 复核", awaiting the user's decision:

- **Jia**: redefine A-4 as deleting shape-1's dead code inside `log.rs`
  (journal / Seal / replay / evict / `Ledger.pages` / `page_first` / filling /
  prepend / seeded / slot / cold / pending). TUI keeps only the fold view.
  Thinner code, one path; costs one careful multi-hundred-line deletion.
- **Yi**: follow the original wording and move the data blocks anyway. Keeps
  DESIGN consistent but buys no behaviour and duplicates window state.

The fallback deletion does not depend on that choice, which is why it was done
first.
