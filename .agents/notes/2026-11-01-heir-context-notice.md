# Heir context-notice delivery

The medium `cmark-part1` run at `.analysis/gongga-heir/raw-heir1` exposed a pending-inbox boundary. A handover completed during step 426 and reset `context_tokens`; at the next step boundary, the notice queued from the old 317,690-token measurement was appended to the empty session. The first heir request consequently contained both the stale order to train an heir and the new lesson ordering it to continue the task. The model stopped after summarising the handover.

A token-only delivery check is insufficient: the request whose tool ran heir writes its pre-handover usage after the tool returns, restoring the old high `context_tokens`. Deleting pending rows in the skill also cannot cover a notice queued from that late write. A ship-side patch was not used because the current ship remote has moved to an unrelated `provider` schema that this server does not have.

The final mechanism is server-owned. A trigger increments `sessions.context_generation` when an existing nonzero `context_tokens` is reset to zero. Context-notice pending payloads carry that generation and their token limit. Usage writes are conditional on the generation captured when their request started, so a response that streamed a handover cannot restore its old measurement. Delivery rejects a marked notice when its generation no longer matches or the current context is below its limit. Ordinary operator and background-job injections retain unconditional delivery. No ship change or new pending-task kind is required.

Validation: 19 store tests and 6 agent tests passed; the existing heir schema gate and fake-provider replay passed. A real-server probe drove `1000 tokens -> generation-0 notice -> reset to generation 1 -> late old usage restored to 1000`: the stale notice was absent from provider requests and stored messages, an ordinary inject and a current generation-1 notice were both delivered, and no pending inject remained. A second real-server probe let the fake provider run the actual heir tool with usage auditing: request inputs were 4128 then 2527 tokens, while session usage writes were 1000 -> 0 -> 2527, proving the first request's 4128 was not written after the reset. The benchmark adapter read the earlier medium run's four handovers into one mentor as four compactions with event timestamps, and zero-heir quick runs remained zero.
